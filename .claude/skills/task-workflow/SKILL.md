# Флоу работы с задачами

Вся работа в проекте строится вокруг `TODO.md`: код меняется только по задачам
из него, а завершение всегда подтверждает пользователь.

## Структура файлов

- `TODO.md` — план задач; секция «Взять в работу» — очередь для выполнения
- `docs/DONE.md`, `docs/JOURNAL.md` — журналы завершённого
- `docs/` — планы крупных задач (например `FEATURE_DEV_PLAN.md`)
- `docs/archive/` — архив планов реализованных задач

## Если файлов нет

Если `TODO.md`, `docs/DONE.md` или `docs/JOURNAL.md` не существуют (например,
в новом проекте) — не продолжай молча и не создавай их сам. Скажи
пользователю, каких файлов не хватает, и предложи создать их с базовой
структурой. После подтверждения создай:

- `TODO.md` — с секцией «Взять в работу»
- `docs/DONE.md`, `docs/JOURNAL.md` — с заголовком и пустым списком

Дальше работай по обычному флоу.

## Взять задачу

Когда пользователь просит взять новую/следующую задачу («возьми новую задачу»,
«следующую», «очередную»):

1. Возьми первый невыполненный (`- [ ]`) пункт из секции «Взять в работу» в
   `TODO.md` — включая подсекции.
2. Сразу пометь его как «в работе» — до любых правок кода.

Если задача содержит несколько под-пунктов — выполняй строго по одному за раз.
После каждого под-пункта остановись и жди пользователя.

## Работа по задаче

- Код (добавление/изменение/удаление) меняется только по задаче из `TODO.md`.
  Без задачи редактируются только документационные файлы: `CLAUDE.md`,
  `TODO.md`, `README.md`, `docs/DONE.md`, `docs/JOURNAL.md` и файлы в `docs/`.
- Когда следующий шаг определён и пользователь явно сказал начинать работу —
  пометь шаг как «в работе» в `TODO.md` до правок кода.
- Крупные задачи могут иметь собственный план реализации в отдельном документе
  в `docs/`. После реализации такой задачи план переносится в `docs/archive/` —
  только по явному запросу пользователя, сам не переноси.
- При формировании планов организуй задачи не по слоям, а сквозными фичами:
  базовый шаг подготовки — фундамент, затем фича за фичей; каждая фича
  заканчивается работающим юзкейсом.

## Завершение

- После реализации пользователь проверяет результат.
- Пункт помечается `[x]` только после явного подтверждения пользователя —
  сам не закрывай задачу.
- После завершения пункта, который меняет структуру компонентов, обнови
  соответствующую схему в `README.md`.
- Если какой-то тест падает — остановись. Не исправляй без явной команды
  пользователя: предложи вариант решения и жди одобрения.

## Баги — отдельный цикл

1. Пользователь описывает баг.
2. Найди первопричину (расследование).
3. Напиши пошаговый план исправления (нумерованные шаги).
4. По запросу добавь шаги плана в секцию «Взять в работу» в `TODO.md`.

## Жёсткие правила

- **Коммиты — только с явным подтверждением пользователя.** Никогда не коммить
  и не пушь по собственной инициативе.
- **TODO/DONE/JOURNAL — только с подтверждением.** `TODO.md`, `docs/DONE.md`,
  `docs/JOURNAL.md` не редактируются без подтверждения пользователя
  (исключение — пометка «в работе» при взятии задачи по флоу выше).
- **Никогда не читай `.env`.** В `.env` реальные секреты (пароли БД, ключи API).
  Если нужно узнать состав переменных — смотри `.env.example`.
